# repoctx 五阶段流水线（实际实现）

> 本文说的每一句都能用 `node scripts/repoctx.mjs pipeline [--out DIR]` 现场复现：它把每阶段耗时与产物计数打出来。
> 数字带日期（2026-09-15），会随提交漂移——**看量级，别引用精确值**。

## 一、产物：一份权威源 + 四个派生视图

| 文件 | 性质 | 入库 |
|---|---|---|
| `.repoctx/map.json` | **唯一权威源**：符号 + 边 + churn + 歧义计数 + ambRefs，不含时间戳（可 0 漂移校验） | 否（可重建） |
| `.repoctx/MAP.md` | 人读投影（`export`；`check` 会校验它是否落后于 map.json） | 是 |
| `.repoctx/notes.jsonl` | 人写经验（`note`），追加式、带日期、不可重建 | 是 |
| `.repoctx/config.json` | 打分白名单与系数（**显式**反馈入口） | 是 |
| `pipeline --out DIR` 的 4 个 JSON | **派生视图**（skeletons / call_graph / scored_symbols / hub_ranking），供外部消费者；不参与判定 | 否 |

## 二、与外部设计的 6 处差异（及理由）

外部设计（分层漏斗 + 4 份缓存 + 反馈闭环）方向大体一致，但有几处我们**刻意不同**：

| # | 外部设计 | 我们的做法 | 理由 |
|---|---|---|---|
| 1 | 落 4 份中间缓存（skeletons/call_graph/scored/hub_ranking，增量更新） | **零缓存**：map.json 一份权威源 + 按需派生 | 多份缓存会互相版本漂移，而我们只有一条漂移校验（`check`）。实测全量重建 2.2 秒，**用 2.2 秒换掉一整类"索引与源码不同步"的 bug 很划算**；增量还要引入失效检测。真需要给外部消费再用 `--out` 导派生视图 |
| 2 | Layer 0 硬删"测试目录下无外部引用的符号" | **降权 ×0.5**，不删 | 测试也是引用，只是证据弱；硬删会让"哪些测试覆盖它"失去答案。枢纽榜要的是排序，不是删除 |
| 3 | Layer 0 硬过滤生成代码 | **暂无该规则**（触发条件已记录） | 实测本仓库**零生成文件**（无 `*_gen.rs` / `.pb.go` / `@generated` 标记）→ 此刻收益为 0。一旦出现，按路径标记加 5 行即可 |
| 4 | Phase 4 计算"组级分数"（候选数惩罚 / 一致性加成 / 项目占比） | 改按**歧义引用热度**排序 | 热度是**可测**信号（无法解析的引用量 = 我们损失了多少召回）；而那几个因子在本仓库几乎恒定（歧义名多为本地 var），加了不改变排序，属未验证的复杂度 |
| 5 | Phase 5 反馈闭环：`auto_deny` / `auto_boost` / `DisambiguationMemory` | **只做显式**（notes.jsonl + config.json） | 隐式学习会让 `map.json` 从"源码的函数"变成"**源码 × 交互史**的函数" → `check` 的 0 漂移保证、跨机器可复现、评审可 diff **全部失效**。我们已经有等价能力的显式版本：声明式、可评审、可回滚 |
| 6 | Phase 1 分类 stdlib / third_party / project | **不索引依赖**，故无此分类 | `listFiles()` 走 `git ls-files` + SKIP_DIR → **所有符号都是项目符号**。该分类在"索引整棵依赖树"的方案里才必要。我们缺的是**引用侧**判别（`.is_empty()` 是 `String` 的还是我们的）——那用 `conf=` 标注诚实暴露，而不是假装解决了 |

## 三、`conf=` 置信度标注（Phase 3/4 的诚实性出口）

in-edges 类结果（`callers` / `impact` / `context`）在两种情况下自我标注：

- `conf="none"` —— **歧义名**（同名多处定义）：引用一律不连边 ⇒ **`n=0` 不代表无人使用**（`impact get` 即此，最危险的空结果）；
- `conf="low"` —— **泛用名**：名字级匹配会混入同名 stdlib 调用（实测抽查 `is_empty` 的 5 个调用方仅 1 个指向本定义）。

这是**标注不是修复**：根因（同名消歧）需要类型解析，即 LSP/SCIP 那条路——成本与实测见 `lsp-bridge-evaluation.md`。

## 四、每阶段耗时实测（2026-09-15 串行基线 / 2026-09-16 并行）

| 阶段 | 耗时（串行） | 占比 |
|---|---|---|
| Phase 1 抽取骨架 | 1976 ms | **91%** |
| Phase 2 名字级调用图 | 149 ms | 7% |
| Phase 3 分层漏斗打分 | 28 ms | 1.3% |
| Phase 4 歧义聚合 + 组内择优 | 9 ms | 0.4% |
| Phase 5 输出 | 0 ms | 0% |
| **合计** | **2162 ms** | |

**并行解析（2026-09-16 已实现）**：`index` 委托子进程 `repoctx-parallel.mjs`（内部 worker_threads 轮转分片，
每 worker 自持一份 WASM parser）；`buildIndex` 保持同步（execFileSync 阻塞取结果），调用点零改动；
**并行/串行产物 SHA256 逐字节一致**（同一 extract，只是执行位置不同）。`REPOCTX_PARALLEL=0` 可强制串行。

**实测收益（诚实数字，远低于当初"4-8x"的猜测——三个假设被测量纠正）**：

| workers | 子进程耗时（322 文件） |
|---|---|
| 1（无并行） | 1774 ms |
| 2 | 1832 ms |
| **4（最优）** | **1588 ms** |
| 8 | 1642 ms |

全量 `index`：2114 ms（串行）→ **约 1.8-1.9 s（~1.15-1.2x）**。为什么只有这么点：

1. **有效核数 4.83**（纯忙循环实测），不是系统报告的 16 —— 沙箱 CPU 配额；
2. **每个 worker 要各自编译 ~6MB WASM 语法**（init 税 ~0.15s/worker），8 路并发互相挤兑，
   实测单 worker init 92ms → 8 路下 1227ms；workers=4 时 init ≈ 0.6s；
3. 只有 Phase 1 可并行，且其中读文件、富化、churn、写盘不可并行（合计 ~0.7s）。

**原生 tree-sitter 替换：2026-09-16 实测后否决**（此前"免编译税可提速"的假设不成立）：

- 安装：prebuilds 全平台齐全（win32-x64/linux-x64 等 24 个 .node，装 2s），但**依赖矩阵碎片化**——
  `tree-sitter-javascript@0.25` 要 runtime `^0.25`、`tree-sitter-rust@0.24` 要 `^0.22.1`，caret 区间不相交
  → npm 永远无法同时装 rust+ts 语法包，只能 `--legacy-peer-deps` 强装混代组合；安装脚本还要求 `node` 在 PATH。
- **速度：原生抽取 3078ms vs WASM 1656ms（慢 1.85x）**。我们的负载是**遍历密集型**
  （数十万次 `descendantsOfType`/`childForFieldName` 跨界调用），原生 N-API 边界开销高于 WASM；
  "原生解析更快"只适用于裸 parse，不适用于本抽取器。init 仅 24ms vs 41ms（无关痛痒）。
- **等价性：69/271 文件抽取结果不同**（差异集中在 TSX）——语法版本代差改变树形，
  产物跨语法版本不稳定，直接违反"同源码 → 同产物"的确定性约定。
- **结论：保持 web-tree-sitter。原生替换 = 更慢 + 不等价 + 依赖更脆，三项全输。**
